# Архитектура игрового ядра Endlock

## 1. Общие сведения

Endlock — двумерная игра в жанре Bullet Heaven / Horde Survival.

Технологический стек проекта:

- Electron — настольное приложение;
- Vue 3 — пользовательский интерфейс;
- TypeScript — основной язык разработки;
- Canvas 2D — отрисовка игрового мира;
- Pinia — планируемое управление состоянием пользовательского интерфейса.

Игровое ядро разрабатывается независимо от Vue и Electron. В основе архитектуры лежат типизированные игровые сущности, отдельные игровые системы и общие контракты взаимодействия между модулями.

## 2. Структура игрового ядра

Игровое ядро располагается в `src/renderer/src/game/`.

| Каталог | Назначение |
|---|---|
| `core` | Основные компоненты и контракты игрового ядра |
| `types` | Общие типы данных |
| `entities` | Игровые сущности |
| `systems` | Реализация игровых систем |
| `input` | Обработка пользовательского ввода |
| `rendering` | Отрисовка игрового мира |
| `weapons` | Оружие и автоматические атаки |
| `progression` | Опыт, уровни и улучшения |
| `levels` | Конфигурации уровней, волны и противники |

## 3. Игровые сущности

Базовым интерфейсом всех объектов игрового мира является `Entity`.

Он содержит идентификатор, тип сущности, положение, радиус коллизии и признак активности.

Дополнительные интерфейсы:

- `MovableEntity` — сущность, обладающая скоростью;
- `LivingEntity` — сущность, обладающая здоровьем.

Конкретные игровые сущности:

- `Player` — игровой персонаж;
- `Enemy` — противник, включая босса;
- `Projectile` — снаряд;
- `Pickup` — подбираемый предмет.

Для препятствий на текущем этапе используется базовый интерфейс `Entity`.

## 4. Состояние игрового мира

Интерфейс `GameWorld` описывает текущее состояние игровой сессии.

Он содержит игрока, массивы противников, снарядов, предметов и препятствий, размеры игрового мира, прошедшее время, статус игры, количество очков и уничтоженных противников.

Возможные состояния игры (`GameStatus`):

- `idle` — сессия не началась;
- `running` — активный игровой процесс;
- `paused` — пауза;
- `level-up` — выбор улучшения;
- `victory` — победа;
- `defeat` — поражение.

## 5. Игровые системы

Игровые системы реализуют интерфейс `GameSystem`:

```typescript
interface GameSystem {
  update(context: GameContext, deltaTime: number): void
}
```

Метод `update` вызывается игровым движком на каждом шаге симуляции.

Интерфейс `GameContext` предоставляет системам следующие ресурсы:

- `world` — состояние игрового мира;
- `events` — шина игровых событий;
- `damage` — сервис нанесения урона;
- `createEntityId()` — получение уникального идентификатора сущности.

## 6. Правила взаимодействия модулей

### 6.1. Создание сущностей

Для получения идентификатора новой сущности необходимо использовать `context.createEntityId()`.

Созданные сущности добавляются в соответствующие массивы игрового мира.

### 6.2. Удаление сущностей

Сущность, подлежащая удалению, помечается как неактивная:

```typescript
entity.active = false
```

Фактическое удаление выполняется системой очистки игрового мира. Не следует удалять элементы из массива непосредственно во время его обхода без учёта последствий такого изменения.

### 6.3. Нанесение урона

Для нанесения урона используется общий сервис:

```typescript
context.damage.applyDamage(target, amount)
```

Не следует самостоятельно уменьшать здоровье цели при реализации атак.

Сервис отвечает за обработку урона, учёт защиты, гибель сущностей и отправку соответствующих событий.

### 6.4. Игровые события

Для взаимодействия независимых модулей используется интерфейс `EventBus`.

Отправка события:

```typescript
context.events.emit({
  type: 'enemy-killed',
  enemy
})
```

Подписка выполняется методом `subscribe`, возвращающим функцию отмены подписки.

Основные события:

- `enemy-killed`;
- `player-damaged`;
- `player-died`;
- `experience-gained`;
- `level-up`;
- `boss-defeated`.

События гибели должны отправляться централизованно и однократно для каждой погибшей сущности.

## 7. Общие единицы измерения

| Величина | Единица измерения |
|---|---|
| Координаты и расстояния | Игровые единицы |
| Радиусы коллизий | Игровые единицы |
| Скорость | Игровые единицы в секунду |
| deltaTime | Секунды |
| Игровое время | Секунды |
| Время жизни снаряда | Секунды |
| Здоровье и урон | Числовые игровые значения |
| Множители характеристик | Безразмерные числа |

Ось X направлена вправо, ось Y — вниз.

Координаты сущностей обозначают положение их центра в игровом мире.

Перемещение рассчитывается с учётом `deltaTime`.

Для первоначального прототипа используются круговые коллизии.

## 8. Распределение ответственности

### Роль 1. Игровое ядро и архитектура

- Игровой цикл.
- Управление игровым миром.
- Обработка ввода.
- Перемещение и камера.
- Коллизии.
- Здоровье и нанесение урона.
- Базовая обработка снарядов.
- Шина событий.
- Отрисовка.
- Интеграция игровых модулей и сборка приложения.

Основные контракты: `GameWorld`, `GameSystem`, `GameContext`, `EventBus`, `DamageService`.

### Роль 2. Оружие и развитие персонажа

- Реализация оружия на основе интерфейса `Weapon`.
- Автоматические атаки.
- Опыт и повышение уровня.
- Улучшения на основе интерфейса `Upgrade`.
- Изменение характеристик `PlayerStats`.
- Начисление очков.
- HUD игрового процесса.

Оружие хранится в массиве `player.weapons`.

Поле `piercing` снаряда обозначает оставшееся количество различных целей, которые он может поразить.

### Роль 3. Уровни и противники

- Конфигурации уровней на основе `LevelConfig`.
- Создание разновидностей противников.
- Волны и появление противников.
- Поведение противников.
- Боссы.
- Игровые карты и связанные ресурсы.

Поле `duration` конфигурации уровня определяет продолжительность основной стадии до появления босса, а не момент автоматической победы.

### Роль 4. Пользовательский интерфейс и сервер

- Главное меню.
- Авторизация.
- Взаимодействие с сервером.
- Хранение результатов.
- Таблица рейтинга.
- Экраны завершения игровой сессии.

Для получения информации о состоянии игры предусматривается интерфейс `GameSnapshot`.

Пользовательский интерфейс не должен напрямую управлять внутренними коллекциями игрового мира.

## 9. Предварительный порядок выполнения систем

1. Обработка пользовательского ввода.
2. Появление противников.
3. Обновление поведения противников.
4. Обновление оружия.
5. Перемещение сущностей.
6. Обработка коллизий.
7. Обработка прогрессии.
8. Удаление неактивных сущностей.
9. Проверка состояния игры.

Отрисовка и обновление пользовательского интерфейса выполняются отдельно от игровой симуляции.

## 10. Архитектурные принципы

При разработке используются:

- разделение ответственности компонентов;
- композиция игровых сущностей;
- полиморфизм через общие интерфейсы;
- инверсия зависимостей;
- разделение интерфейсов;
- слабая связанность модулей посредством событий;
- разделение игровой логики и пользовательского интерфейса.

Для организации пользовательского интерфейса планируется подход на основе принципов MVVM.

## 11. Соглашения разработки

- Названия классов, интерфейсов, функций, переменных и файлов пишутся на английском языке.
- Документация, комментарии и описания изменений пишутся на русском языке.
- Разработка ведётся в отдельных ветках Git.
- Изменения объединяются с основной веткой через Pull Request.
- Перед отправкой изменений выполняется `npm run typecheck`.
- Для коммитов используются префиксы `feat:`, `fix:`, `refactor:`, `docs:`, `chore:` и другие в соответствии с назначением изменений.

Изменения общих контрактов необходимо согласовывать с участниками команды.
